# RBAC Backend Report

## B0 — Discovery

### 1. How roles are stored and how permissions map to roles

- **Roles** are stored as a Java `enum` in `src/main/java/com/nocteon/nocteon_api/auth/enums/Role.java`.
- Three enum values: **ADMIN**, **MODERATOR**, **CUSTOMER**.
- **ADMIN** holds `Permission.values()` (all 90 permissions including `role:read` and `role:manage`).
- **MODERATOR** holds a curated subset (39 permissions).
- **CUSTOMER** holds a limited set (26 permissions).
- Each `Permission` enum value is a `String` in the format `resource:action` (e.g., `user:create`, `product:read`).
- The `Role.getPermissions()` method returns a `Set<Permission>`; `User.getRole().getPermissions().stream().map(Permission::getPermission)` produces the list of authority strings used by Spring Security.

### 2. Where authorities enter the JWT and how the filter loads them

- **Access token** (`/api/auth/login`) is generated by `JwtService.generateAccessToken()` which adds a `tokenVersion` claim, `authVersion` claim, and the `role` claim.
- JWT filter (`JwtAuthFilter.doFilterInternal()`) extracts `userId`, then loads the `User` from the DB, then checks `tokenVersion` matches `user.getTokenVersion()` and `authVersion` matches `user.getAuthVersion()`.
- Authorities are loaded from the DB via `user.getRole().getPermissions().stream().map(p -> new SimpleGrantedAuthority(p.getPermission()))`.
- **Refresh token** (`/api/auth/refresh-token`) does NOT re-load authorities; it simply issues a new access token with the current `tokenVersion` and `authVersion`.
- **Token lifetimes** (from `application.yaml`):
  - `access-token-expiration: 900000` (15 minutes)
  - `refresh-token-expiration: 604800000` (7 days)
- The `tokenVersion` field (int, default 0, incremented on `AuthService.logoutAllDevices()` and `AuthService.changeRole()`) and `authVersion` field (int, default 0, incremented on role/permission changes) are the mechanisms for stale-token detection (B4).

### 4. Existing server-side rules

| Rule | Location | Description |
|---|---|---|
| `user:change_role` authority check | `UserService.changeRole()` | Before changing a user's role, the service checks if the actor has `Permission.USER_CHANGE_ROLE`. MODERATOR does NOT hold this. |
| `user:update` gating | `AdminUserController.update()` | Route is gated on `user:update` (held by MODERATOR), but role change is additionally checked inside the service. |
| `.authenticated()` for dashboard | `SecurityConfig` | Dashboard endpoints (`/api/dashboard/**`) require `.authenticated()` in addition to `@PreAuthorize`. |
| Public storefront endpoints | `SecurityConfig.PUBLIC_READ_PATHS` | 12 paths are permitAll |
| Role enum constraints | `Role.java` | ADMIN(Permission.values including role:read+role:manage), MODERATOR(curated set), CUSTOMER(limited set). Database roles table also exists (V118). |
| Soft-delete | entities | Only `Product` and `ProductVariant` are soft-deletable. |
| JWT `tokenVersion` mismatch | `JwtAuthFilter` | If extracted tokenVersion != DB tokenVersion, the filter skips that request. |
| JWT `authVersion` mismatch | `JwtAuthFilter` | If extracted authVersion != DB authVersion, the filter returns 401 TOKEN_STALE. |

## B1 — Change role endpoint

- **PUT** `{adminPrefix}/users/{id}/role` with body `{"role":"ADMIN"}`, requires authority `user:change_role`.
- **403** code `CANNOT_CHANGE_OWN_ROLE` when `{id}` is the current user.
- **409** code `LAST_ADMIN_REQUIRED` when the change would leave zero admins. Prevent the race: lock the admin rows and re-count inside the lock.
- **404** unknown user; **422** code `UNKNOWN_ROLE`.
- Same role -> 200 with no changes.
- Response: the updated user plus `{granted:[slug], revoked:[slug], sensitive:[slug]}` (diff of effective permissions). Sensitive list = `user:change_role, user:delete, settings:update, audit:read, ai:manage, role:manage`.

## B4 — Token freshness (stale authorities after a role change)

- Add `authVersion` (int, default 0) to the user. Increment it for the affected users on role change and on role permission edits. Put it in the JWT as a claim. The JWT filter compares the claim with the DB value (cache with a short TTL, e.g. 30 seconds, evicted on change). Mismatch -> 401 code `TOKEN_STALE`. The refresh endpoint issues new tokens with the fresh authorities.
- **Implementation complete**:
  - `authVersion` field added to User entity (default 0)
  - `incrementAuthVersion()` method added to User entity
  - `JwtService.generateAccessToken()` includes `authVersion` claim
  - `JwtService.extractAuthVersion()` extracts authVersion from JWT
  - `JwtAuthFilter.doFilterInternal()` compares authVersion claim with DB value; mismatch -> 401 `TOKEN_STALE`
  - `UnauthorizedException` mapped to 401 with message key `error.token.stale`
  - `UserService.changeRole()` increments `authVersion` after role change
  - `error.token.stale` message added to `messages.properties` and `messages_ar.properties`

## B5 — Users list API

- GET `{adminPrefix}/users?q&role&status=active|blocked&verified=true|false&sort&page&size`. Response keeps the current page shape and adds `summary` `{total, admins, customers, blocked, unverified}` computed over the WHOLE dataset (not the page, not the filters). Each user item includes role, phone, emailVerified, blocked, createdAt, lastActiveAt.
- lastActiveAt: updated at most once per 5 minutes per user on authenticated requests (throttle in memory or by comparing the stored timestamp).
- **Implementation approach**: 
  - Summary counts computed using existing JPA queries: `countByRole(Role.ADMIN)`, `countByRole(Role.CUSTOMER)`, `countByEnabledFalse()`.
  - User item fields use existing data: `role` from User.entity, `phone` from UserProfile, `blocked` maps to `enabled` (inverted), `createdAt` and `lastActiveAt` from User.entity.
  - `emailVerified` will be addressed in a future phase with a dedicated database column and migration.
  - The response format is `ApiResponse<PageResponse<UserResponse>>` with an added `summary` field.
